# AUDITO

Este skill (nombre técnico `click-path-audit`) sirve para encontrar bugs de comportamiento que la lectura estática del código o el debugging tradicional no detectan: funciones que individualmente funcionan bien pero que, al ejecutarse en secuencia, se cancelan entre sí, dejan el estado final incorrecto, o dejan la UI en un estado inconsistente. Se usa típicamente cuando un debugging sistemático no encontró ningún bug pero los usuarios reportan botones "rotos", o después de un refactor grande que toca estado compartido (stores tipo Zustand/Redux/context).

El problema que resuelve: el debugging clásico solo chequea si el handler existe, si no crashea y si devuelve el tipo correcto de dato. No chequea si el estado final de la UI coincide con lo que promete la etiqueta del botón, ni si una función B deshace silenciosamente lo que hizo la función A a través de efectos secundarios en estado compartido. El ejemplo real que inspiró el skill: un botón "New Email" llamaba `setComposeMode(true)` y luego `selectThread(null)`; ambas funciones "funcionaban", pero `selectThread` tenía un efecto secundario que reseteaba `composeMode` a false, por lo que el botón no hacía nada visible. Ese bug pasó desapercibido entre otros 54 bugs hallados por debugging sistemático.

Cómo funciona (metodología): para cada punto de interacción del usuario (botón, toggle, submit, etc.) en el área objetivo hay que: 1) identificar el handler (onClick, onSubmit, onChange...), 2) trazar cada llamada a función dentro del handler en orden, 3) para cada llamada determinar qué estado lee, qué estado escribe, y si tiene efectos secundarios que resetean/limpian otro estado, 4) verificar si alguna llamada posterior deshace un cambio hecho por una llamada anterior, 5) verificar si el estado final coincide con lo que el usuario espera según la etiqueta del botón, y 6) chequear condiciones de carrera en llamadas asíncronas que puedan resolver en orden incorrecto.

El workflow de ejecución tiene tres pasos. Paso 1, "Map State Stores": antes de auditar cualquier touchpoint hay que construir un mapa de efectos secundarios de cada store de estado (Zustand/context), documentando para cada acción/setter qué campos setea y cuáles resetea como efecto colateral, con un formato de salida tipo `actionName → {sets: [...], resets: [...]}` y una sección aparte de "DANGEROUS RESETS" (acciones que limpian estado que no les pertenece). Este mapa es la referencia crítica sin la cual el bug del ejemplo sería invisible. Paso 2, "Audit Each Touchpoint": para cada botón/toggle/submit se documenta el touchpoint, el handler paso a paso, lo esperado vs. lo real, y el veredicto, chequeando específicamente seis patrones de bug: (1) Sequential Undo (una llamada posterior resetea lo que seteó una anterior), (2) Async Race (dos promesas que setean el mismo estado y el resultado final depende de cuál resuelve primero), (3) Stale Closure (un useCallback captura un valor de estado obsoleto y llamadas repetidas no incrementan como se espera), (4) Missing State Transition (el botón dice "Save"/"Delete"/"Send" pero el handler no ejecuta realmente la acción, solo valida o setea un flag), (5) Conditional Dead Path (un if nunca se cumple porque la condición siempre es falsa en ese punto), y (6) useEffect Interference (un useEffect que observa el estado que el botón acaba de setear y lo revierte). Paso 3, "Report": cada bug encontrado se documenta con un ID tipo `CLICK-PATH-NNN`, severidad (CRITICAL/HIGH/MEDIUM/LOW), touchpoint, patrón, handler, traza de llamadas con el conflicto marcado, estado esperado vs. actual, y el fix específico.

Sobre el control de alcance: esta auditoría es costosa computacionalmente, así que se recomienda escalarla según el caso — auditoría completa de la app (al lanzar o tras un refactor mayor, lanzando agentes en paralelo por página), auditoría de una sola página (tras construir una página nueva o un reporte de botón roto), o auditoría enfocada en un store (tras modificar una acción de Zustand, auditando todos sus consumidores). Para una auditoría completa se sugiere un split de agentes: un Agente 1 dedicado exclusivamente a mapear todos los stores de estado (Paso 1), cuyo output es contexto obligatorio y debe completarse ANTES que el resto; y luego agentes 2 a 8 cubriendo áreas funcionales distintas de la app (Dashboard, Chat, Emails, Projects, CRM, Profile/Settings/Vault/Notifications, Management Suite).

Cuándo usarlo: después de que un debugging sistemático no encuentre bugs pero haya reportes de UI rota; tras modificar cualquier acción de un store Zustand (revisando todos los llamadores); tras cualquier refactor que toque estado compartido; antes de un release, sobre flujos críticos de usuario; y siempre que un botón "no hace nada" — es la herramienta específica para ese síntoma.

Cuándo NO usarlo: para bugs a nivel API (forma de respuesta incorrecta, endpoint faltante) se recomienda usar `systematic-debugging` en su lugar; para problemas de estilos/layout, inspección visual; para problemas de performance, herramientas de profiling.

El skill también documenta su integración con otros skills del mismo ecosistema: se ejecuta DESPUÉS de `/superpowers:systematic-debugging` (que encuentra otros tipos de bugs), ANTES de `/superpowers:verification-before-completion` (que verifica que los fixes funcionen), y alimenta a `/superpowers:test-driven-development`, ya que cada bug encontrado debería derivar en un test. Cierra con el ejemplo completo y comentado del bug de "New Email" en `ThreadList.tsx`, mostrando el código del handler, la definición del store con el reset silencioso de `composeMode`, y una explicación de por qué el debugging sistemático lo pasó por alto (el handler no está muerto, ambas funciones existen, ninguna crashea, los tipos son correctos) mientras que el click-path audit sí lo detecta siguiendo los pasos 1 y 2 de su metodología.
