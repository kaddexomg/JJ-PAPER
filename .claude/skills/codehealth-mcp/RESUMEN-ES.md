# codehealth-mcp

Este skill integra el servidor MCP de CodeScene (`codehealth-mcp`) para dar retroalimentación en tiempo real sobre la "salud de código" (Code Health) a nivel estructural y de diseño, complementando skills de estilo/lint como `coding-standards` y `plankton-code-quality`. No evalúa formato ni convenciones, sino mantenibilidad estructural: complejidad, tamaño de funciones, acoplamiento, etc. El paquete upstream es `@codescene/codehealth-mcp` (repositorio `codescene-oss/codescene-mcp-server`), y se ejecuta vía stdio con `npx`.

Seguridad y límites: en ECC este MCP es opt-in, la entrada `codescene` en `mcp-configs/mcp-servers.json` es solo una plantilla que hay que copiar manualmente si se quiere usar (se puede excluir con `ECC_DISABLED_MCPS=codescene`). No trae token incluido: hay que configurar `CS_ACCESS_TOKEN` uno mismo (siguiendo la doc upstream) y nunca commitear el token. Las herramientas solo analizan archivos y estado de git del repo local al que se apunta (rutas pasadas explícitamente, más contexto de rama para `analyze_change_set`); no se ejecutan por sí solas. No debe usarse sobre secretos, credenciales o rutas que no se quieran analizar. Si el MCP no está disponible (offline, token inválido, servidor caído), la instrucción explícita es NO inventar puntajes de Code Health: avisar al usuario que el chequeo se saltó, continuar solo con aprobación explícita, y preferir lint/tests/`verification-loop` como gate mientras tanto.

Cuándo usarlo (triggers / auto-activación en ECC): cuando el usuario pide revisar calidad de código, refactorizar un archivo, o verificar si cambios hechos por IA degradaron la mantenibilidad; antes de editar un "hotspot", módulo legacy o archivo desconocido; antes de un commit o pull request como salvaguarda de mantenibilidad; después de un diff grande generado por un agente, para verificar que no hubo regresión. Se combina con `verification-loop`, `tdd-workflow` o `/quality-gate` como chequeo estructural adicional, no como reemplazo de tests/lint.

Cómo funciona (workflow):
1. Conectar el servidor MCP: copiar el bloque `codescene` en la config MCP del harness (`~/.claude.json` → `mcpServers` para Claude Code, o `.mcp.json` a nivel de repo), con `command: npx`, `args: ["-y", "@codescene/codehealth-mcp"]` y `env.CS_ACCESS_TOKEN`. Reiniciar la sesión y confirmar que el servidor esté conectado antes de confiar en los puntajes. El modo standalone no requiere cuenta paga de la plataforma CodeScene para las cuatro herramientas soportadas.
2. Usar solo las herramientas "standalone": `code_health_review` (análisis estructural completo antes de modificar un archivo), `code_health_score` (puntaje numérico rápido tras cada cambio, para ver el delta), `pre_commit_code_health_safeguard` (bloquea commits que introducen regresiones) y `analyze_change_set` (chequeo a nivel de rama antes de abrir un PR). No se deben usar herramientas solo de plataforma (p. ej. listas de hotspots de deuda técnica de todo el repo) ni referenciar `delta_analysis`, que no existe en modo standalone.
3. Interpretar los puntajes, en escala 1–10: 9.0–10.0 es verde/sano (más seguro extender, igual preferir cambios acotados); 4.0–8.9 es amarillo/con deuda (avanzar con cuidado, nada de refactors "de paso"); 1.0–3.9 es rojo/deuda severa (alcance muy limitado).
4. Ciclo de feedback: antes de tocar un archivo, correr `code_health_review`, registrar el puntaje base y los "code smells" listados, y planear el cambio más pequeño posible (si el puntaje es menor a 5: diff mínimo; entre 5 y 7: sin refactors amplios; mayor a 7: más seguro refactorizar, pero verificando después de cada edición). Después de cada cambio, correr `code_health_score` sobre el mismo archivo y comparar contra el baseline; si el puntaje bajó, hay que corregirlo antes de seguir — nunca se debe dar la tarea por terminada con un puntaje peor que al inicio. Antes de cada commit, correr `pre_commit_code_health_safeguard` sobre el repo. Antes de un PR, correr `analyze_change_set` contra la rama base (p. ej. `main`).

Ejemplos incluidos en el doc: un caso real sobre el repo `pallets/flask` donde, siguiendo el loop completo (review → refactor dirigido → score tras cada edición → safeguard antes de commit → analyze_change_set antes de PR), el puntaje de Code Health subió de 4.82 a 9.1 usando solo el token gratuito standalone. También se sugiere un bloque de texto para pegar en `AGENTS.md` o `CLAUDE.md` que fuerza estas reglas como política del proyecto. Y se listan antipatrones a evitar: editar primero y revisar después sin `code_health_review`; ignorar una caída de puntaje solo porque los tests pasan; hacer refactors amplios sobre un archivo en rango rojo (menor a 5). El flujo correcto es siempre: review → cambio chico → score → safeguard de commit → analyze_change_set.

Relación con otros skills de ECC: `coding-standards` cubre estilo/nombres mientras este skill cubre estructura/complejidad; `plankton-code-quality` es lint/formato en tiempo de escritura, este es un gate estructural pre/post edición; se integra con `verification-loop`/`/quality-gate` como chequeo adicional de regresión; se puede combinar con `security-review` (seguridad vs. mantenibilidad); y con `tdd-workflow`, remarcando que tests en verde no implica buen diseño, por lo que conviene revisar el puntaje tras refactors. Recomendación de contexto: ECC sugiere mantener bajo el número de MCPs activos, por lo que conviene habilitar `codescene` solo cuando se hacen ediciones sustanciales y deshabilitarlo el resto del tiempo.
