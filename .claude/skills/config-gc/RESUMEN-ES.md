# config-gc

Este skill implementa una "recolección de basura" (garbage collection) para la configuración de Claude Code almacenada en `~/.claude`, inspirada en el concepto de GC de los runtimes de programación: escanea periódicamente en busca de elementos que ya no se usan, están duplicados, obsoletos o aportan poco valor, y guía al usuario para liberar ese espacio. La diferencia clave respecto al GC de software es que aquí la recolección siempre requiere intervención humana: el skill nunca borra nada de forma autónoma.

Se activa cuando el usuario pide limpiar, auditar o reducir su configuración de Claude Code, cuando se queja de tener demasiados skills, hooks ruidosos o un arranque de sesión lento, cuando toca una revisión periódica (mensual) del setup, o después de instalar un paquete grande de skills para detectar solapamientos con lo ya existente. No debe activarse para limpiar código fuente de proyectos (eso es refactorización), para borrar el historial de chat, ni para desinstalar Claude Code.

La filosofía de diseño se basa en seis principios: 1) las configuraciones "append-only" (skills, memoria, hooks, permisos) solo crecen y se pudren en silencio si no se revisan; 2) conviene hacer auditorías regulares (cada ~30 días) proponiendo un lote pequeño de candidatos por vez, en lugar de purgas únicas; 3) cada canal de acumulación tiene sus propias señales de obsolescencia, por lo que no se aplica una regla única a todos; 4) siempre se prioriza el "soft-delete": primero renombrar a `.disabled`, luego mover a `~/.claude/_gc_trash/`, y recién como última opción el borrado real, manteniendo siempre una vía de deshacer; 5) confirmación humana obligatoria ítem por ítem con `[y/n/skip]`, sin atajos de "aceptar todo"; 6) se mantiene un registro (`~/.claude/gc_log.md`) de cada corrida, indicando qué se tocó, por qué y cómo deshacerlo.

El skill define ocho canales de escaneo, cada uno con sus señales propias de redundancia/obsolescencia: (1) Skills en `~/.claude/skills/*/` (nombres solapados, nunca disparados en transcripciones recientes, SKILL.md roto o vacío); (2) Memoria en archivos `.md` y su índice (entradas duplicadas, contenido contradictorio, fechas vencidas, archivos huérfanos, fragmentos muy cortos); (3) Hooks (scripts en disco no referenciados por ninguna config); (4) Permisos en `settings.json`/`settings.local.json` (entradas duplicadas o ya cubiertas por un wildcard como `Bash(*)`); (5) Servidores MCP que fallan al conectar o están duplicados; (6) Recordatorios/jobs programados vencidos o cuyo script objetivo ya no existe; (7) Historial de proyectos con snapshots obsoletos; (8) Cachés de runtime (`cache/`, `file-history/`, `logs/`, `shell-snapshots/`), priorizando por tamaño y antigüedad.

El flujo de trabajo tiene seis pasos: escanear todos los canales (o el subconjunto pedido) recolectando candidatos con ruta, canal, señal, tamaño y fecha de modificación; rankear por confianza (roto/huérfano = alta, simplemente viejo = baja), presentando como tabla numerada con un tope de ~20 candidatos por corrida; confirmar uno por uno mostrando evidencia y preguntando `[y/n/skip]`, pudiendo el usuario detenerse en cualquier momento; aplicar soft-delete a los confirmados (rename `.disabled` para skills/hooks, mover a `_gc_trash/<fecha>/` para archivos; para permisos, que están en JSON sin comentarios, se hace backup del archivo, se registra la entrada eliminada en el log y se quita del array `allow` con `jq`; solo se hace hard-delete si el usuario lo pide explícitamente); registrar la corrida en `gc_log.md` con timestamp, ítems accionados e instrucciones de deshacer; y finalmente reportar el espacio recuperado, los canales que siguen sanos y sugerir la próxima fecha de revisión.

El documento incluye ejemplos concretos de comandos bash: detectar scripts de hooks huérfanos comparándolos contra las configs con `grep`; detectar permisos redundantes o duplicados con `jq` (incluyendo detectar entradas `Bash(...)` ya cubiertas por `Bash(*)`); encontrar cachés viejas grandes con `find -mtime +30` combinado con `du -k` (evitando `-printf`, que es GNU-only, para compatibilidad con macOS/BSD); mover un skill muerto a `_gc_trash/<fecha>/` registrando la acción en el log; y eliminar una entrada de permiso confirmada haciendo backup del `settings.local.json`, logueando la acción y aplicando `jq '.permissions.allow -= [...]'`.

Como anti-patrones se señalan: aprobar en bloque ("¿borrar los 15? [y/n]"), que rompe el diseño de una decisión por ítem; hacer hard-delete en el primer intento sin pasar por `_gc_trash/` o `.disabled`; tratar "viejo" como sinónimo de "muerto" (un skill sin uso en 60 días puede ser estacional, como impuestos o revisiones trimestrales); limpiar memoria por truncamiento en vez de leer y fusionar contenido contradictorio conservando la verdad más reciente; y tocar cualquier cosa fuera de `~/.claude` (o del `.claude/` del proyecto), ya que este skill nunca debe intervenir en árboles de código fuente.

Como buenas prácticas recomienda correr el GC no solo por calendario sino después de instalaciones grandes (por ejemplo, un paquete de 50 skills, momento típico donde aparecen solapamientos); al detectar dos skills solapados, preferir desactivar el que tenga la descripción de disparo más débil (probablemente el que casi nunca se activaba); priorizar la limpieza de permisos como el canal de mayor valor por minuto invertido, ya que las entradas redundantes dificultan la revisión de seguridad; y conservar `gc_log.md` indefinidamente, dado su bajo costo de espacio y la utilidad de poder consultar cuándo y por qué se desactivó algo.

Finalmente, el skill lista relaciones con otros skills: `skill-stocktake` audita la calidad de los skills (config-gc audita su existencia, y stocktake debería correr sobre lo que sobrevive al GC); `workspace-surface-audit` es el complemento aditivo, ya que recomienda qué instalar mientras config-gc es la mitad sustractiva del mismo ciclo de vida; `configure-ecc` sugiere correr config-gc después de instalar skills para reconciliar solapamientos con el setup preexistente; `continuous-learning` produce los archivos de memoria que este skill luego audita; y `security-review` se complementa bien con el canal de permisos.
