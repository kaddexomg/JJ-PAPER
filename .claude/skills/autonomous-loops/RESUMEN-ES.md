# autonomous-loops

Este skill documenta patrones y arquitecturas para ejecutar Claude Code de forma autónoma en bucles, desde pipelines secuenciales simples hasta orquestación multi-agente en forma de DAG guiada por RFC. Nota de compatibilidad: en la v1.8.0 el nombre canónico pasó a ser `continuous-agent-loop`; este skill se mantiene por una versión para no romper flujos existentes, pero la guía nueva debe crearse en el otro skill.

Sirve para elegir e implementar la arquitectura de loop adecuada según la complejidad del problema: desarrollo autónomo sin intervención humana, pipelines tipo CI/CD, agentes en paralelo con coordinación de merge, persistencia de contexto entre iteraciones y pasadas de control de calidad ("quality gates").

Presenta un espectro de seis patrones, de menor a mayor complejidad:

1. **Sequential Pipeline (`claude -p`)**: encadenar llamadas no interactivas de `claude -p`, cada una con un prompt enfocado (implementar, limpiar, verificar, commitear). Principios clave: cada paso usa contexto fresco (sin "bleed"), el orden importa porque cada paso parte del estado de archivos dejado por el anterior, evitar instrucciones negativas (mejor un paso de limpieza separado), y usar `set -e` para propagar fallos. Admite variaciones: ruteo de modelos (Opus para investigar/revisar, Sonnet para implementar), paso de contexto vía archivos en lugar de prompts largos, y restricción de herramientas con `--allowedTools`.

2. **NanoClaw REPL**: loop persistente propio de ECC (`node scripts/claw.js`), un REPL con memoria de sesión que llama a `claude -p` de forma síncrona pasando el historial completo guardado en `~/.claude/claw/{session}.md` (Markdown como base de datos). Útil para exploración interactiva con persistencia de sesión; menos apto para CI/CD que el pipeline secuencial.

3. **Infinite Agentic Loop**: sistema de dos prompts (orquestador + subagentes) para generación paralela guiada por especificación (crédito: @disler). El orquestador lee un spec, escanea el directorio de salida para hallar el número de iteración más alto, y despliega N subagentes en paralelo, cada uno con dirección creativa única y número de iteración asignado (para evitar duplicados). Se implementa como comando de Claude Code (`.claude/commands/infinite.md`) y se invoca con `/project:infinite spec output_dir count`. Estrategia de lotes: 1-5 agentes simultáneos, 6-20 en lotes de 5, modo infinito en oleadas de 3-5 hasta agotar contexto. Insight clave: la unicidad se logra por asignación explícita del orquestador, no por autodiferenciación de los agentes.

4. **Continuous Claude PR Loop**: script de producción (crédito: @AnandChowdhary) que corre en loop continuo creando ramas, ejecutando `claude -p`, opcionalmente una pasada de revisor, commiteando, abriendo PR, esperando CI, auto-arreglando fallas de CI y mergeando, con límites por `--max-runs`, `--max-cost`, `--max-duration` o señal de finalización. Usa un archivo `SHARED_TASK_NOTES.md` como puente de contexto entre iteraciones independientes (Claude lo lee al inicio y lo actualiza al final). Ante fallas de CI, recupera logs con `gh run view`, corrige, commitea y reintenta hasta `--ci-retry-max`. Soporta paralelismo vía worktrees de git. Advertencia: instalar el script tras revisar el código, nunca "pipear" scripts externos directo a bash.

5. **De-Sloppify Pattern**: patrón complementario para cualquier loop. Agrega una pasada de limpieza dedicada después de cada paso de implementación, en vez de agregar instrucciones negativas al prompt del implementador (lo cual degrada la calidad de forma impredecible). La pasada de limpieza elimina tests que verifican el sistema de tipos o comportamiento del framework en vez de lógica de negocio, chequeos redundantes, manejo de errores excesivo, `console.log` y código comentado, corriendo el test suite después. Insight: dos agentes enfocados superan a uno constreñido.

6. **Ralphinho / RFC-Driven DAG Orchestration**: el patrón más sofisticado (crédito: @enitrat). Descompone un RFC/PRD en unidades de trabajo con un DAG de dependencias (`WorkUnit` con id, deps, criterios de aceptación y tier de complejidad: trivial/small/medium/large). Cada capa del DAG se ejecuta en un "Ralph loop" de hasta 3 pasadas: pipelines de calidad en paralelo por unidad (cada una en su propio worktree, usando jj/Jujutsu) que recorren research → plan → implement → test → review según el tier, seguidos de una cola de merge que rebasa contra main, corre tests, y aterriza o "evict" (expulsa) unidades con conflicto, devolviendo el contexto del conflicto al implementador para el siguiente intento. Cada etapa corre en un agente y modelo distintos (p. ej. Sonnet para research/test, Opus para plan/code review, Codex para implementar/corregir) para eliminar el sesgo de autor, ya que el revisor nunca escribió el código que revisa. El estado completo se persiste en SQLite para poder retomar el trabajo. Se recomienda usarlo cuando hay múltiples unidades interdependientes, se necesita implementación paralela o hay riesgo de conflictos de merge; para cambios de un solo archivo o iteración rápida conviene un patrón más simple.

El documento incluye una matriz de decisión para elegir el patrón según si la tarea es un cambio único, si existe un RFC/spec escrito, si se necesita paralelismo o muchas variaciones de lo mismo. También explica cómo combinar patrones (por ejemplo, Sequential Pipeline + De-Sloppify, Continuous Claude + De-Sloppify, o cualquier loop + verificación con el comando `/verify` o el skill `verification-loop`), y cómo aplicar el enfoque por tiers de Ralphinho incluso en loops simples (rutear tareas simples a Haiku y las complejas a Opus).

Finalmente, lista anti-patrones a evitar: loops infinitos sin condición de salida, falta de puente de contexto entre iteraciones, reintentar la misma falla sin capturar el error, usar instrucciones negativas en vez de pasadas de limpieza, meter todos los agentes en una sola ventana de contexto (el revisor nunca debería ser el autor), e ignorar el solapamiento de archivos en trabajo paralelo sin estrategia de merge. Cierra con una tabla de referencias y créditos a los proyectos originales (Ralphinho, Infinite Agentic Loop, Continuous Claude, NanoClaw y Verification Loop de ECC).
