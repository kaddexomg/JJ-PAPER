# agent-sort

Este skill sirve para armar un plan de instalación de ECC (Everything Claude Code) adaptado a un repositorio específico, en lugar de cargar el bundle completo. Su objetivo es clasificar los componentes de ECC (skills, comandos, rules, hooks y "extras") con evidencia concreta extraída del propio código del repo, no en base a intuición o preferencias genéricas.

Se usa cuando: un proyecto solo necesita un subconjunto de ECC y la instalación completa resulta demasiado ruidosa; el stack del repo está claro pero nadie quiere curar los skills uno por uno a mano; un equipo quiere una decisión de instalación repetible y respaldada por evidencia (grep) en lugar de opinión; hace falta separar superficies que se cargan siempre ("daily") de superficies de referencia buscables ("library"); o un repo se desvió hacia lenguajes, rules o hooks equivocados y necesita limpieza.

Reglas no negociables: usar el repo actual como fuente de verdad; toda decisión DAILY debe citar evidencia concreta del repo; LIBRARY no significa "borrar" sino "mantener accesible sin cargarlo por defecto"; no instalar hooks, rules o scripts que el repo actual no pueda usar; y preferir superficies nativas de ECC, sin introducir un segundo sistema de instalación paralelo.

El modelo de clasificación usa solo dos categorías: DAILY (debe cargarse en cada sesión de ese repo, porque coincide fuertemente con su lenguaje, framework, workflow u operador) y LIBRARY (útil de conservar pero no vale la pena cargarlo por defecto; debe seguir siendo accesible por búsqueda, por un router skill, o por uso manual selectivo).

Como fuentes de evidencia se usan: extensiones de archivo, package managers y lockfiles, configuraciones de framework, configuraciones de CI y hooks, scripts de build/test, imports y manifiestos de dependencias, y documentación del repo que describa explícitamente el stack. Se sugieren comandos como `rg --files`, `rg -n "typescript|react|next|supabase|django|spring|flutter|swift"`, y `cat` sobre archivos como package.json, pyproject.toml, Cargo.toml, pubspec.yaml o go.mod.

Si hay subagentes paralelos disponibles, la revisión se divide en pasadas: (1) Agents — clasificar agents/*; (2) Skills — clasificar skills/*; (3) Commands — clasificar commands/*; (4) Rules — clasificar rules/*; (5) Hooks y scripts — clasificar hooks, chequeos de salud de MCP, scripts auxiliares y compatibilidad de SO; (6) Extras — clasificar contexts, ejemplos, configs de MCP, templates y docs de guía. Si no hay subagentes, las mismas pasadas se corren de forma secuencial.

El flujo de trabajo central tiene seis pasos: 1) Leer el repo para establecer el stack real (lenguajes, frameworks, package manager principal, stack de testing, lint/format, superficie de deploy/runtime, integraciones de operador ya presentes). 2) Construir una tabla de evidencia por cada componente candidato, con columnas: ruta del componente, tipo, bucket propuesto, evidencia del repo y justificación breve (se da un formato de ejemplo tipo tabla en texto plano). 3) Decidir DAILY vs LIBRARY: se promueve a DAILY cuando el repo usa claramente el stack correspondiente, el componente es suficientemente general para ayudar en toda sesión, o el repo ya depende del runtime/workflow asociado; se degrada a LIBRARY cuando el componente está fuera de stack, podría necesitarse más adelante pero no a diario, o agrega sobrecarga de contexto sin relevancia inmediata. 4) Construir el plan de instalación, traduciendo la clasificación en acciones concretas (instalar o mantener skills DAILY en `.claude/skills/`, mantener comandos DAILY solo si siguen siendo útiles como shims explícitos, instalar solo los sets de rules del lenguaje que coincide, conservar solo hooks/scripts compatibles, y mantener las superficies LIBRARY accesibles vía búsqueda o router); si el repo ya usa instalaciones selectivas, se debe actualizar ese plan existente en vez de crear un sistema nuevo. 5) Crear opcionalmente un router de biblioteca en `.claude/skills/skill-library/SKILL.md`, que debe incluir una breve explicación de DAILY vs LIBRARY, palabras clave de disparo agrupadas, y dónde viven las referencias de biblioteca, sin duplicar el cuerpo completo de cada skill dentro del router. 6) Verificar el resultado: confirmar que cada archivo DAILY existe donde se espera, que no quedaron rules de lenguajes obsoletos activas, que no se instalaron hooks incompatibles, y que la instalación resultante coincide realmente con el stack del repo; se debe devolver un reporte compacto con conteo de DAILY, conteo de LIBRARY, superficies obsoletas removidas y preguntas abiertas.

Los outputs a producir, en orden, son: inventario DAILY, inventario LIBRARY, plan de instalación, reporte de verificación y, opcionalmente, el router `skill-library`.

En cuanto a handoffs a otros skills: si el siguiente paso es instalación interactiva o reparación, se deriva a `configure-ecc`; si el siguiente paso es limpieza de solapamientos o revisión de catálogo, se deriva a `skill-stocktake`; si el siguiente paso es una reducción de contexto más amplia, se deriva a `strategic-compact`.

Finalmente, el formato de salida esperado sigue una estructura fija con las secciones: STACK (resumen de lenguaje/framework/runtime), DAILY (ítems de carga permanente con evidencia), LIBRARY (ítems buscables/de referencia con evidencia), INSTALL PLAN (qué instalar, remover o enrutar) y VERIFICATION (chequeos realizados y brechas pendientes).
