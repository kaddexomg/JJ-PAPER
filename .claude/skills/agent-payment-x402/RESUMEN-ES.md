# agent-payment-x402

Este skill permite que agentes de IA ejecuten pagos reales de forma controlada, usando el protocolo HTTP x402 y herramientas MCP, de modo que un agente pueda pagar por APIs externas, servicios o incluso a otros agentes sin manejar fondos de forma custodial. El objetivo central es habilitar pagos "policy-gated": el agente solo puede gastar dentro de límites definidos previamente por un orquestador, nunca por sí mismo.

Conviene usarlo cuando el agente necesita pagar una llamada a una API con cobro por uso, comprar un servicio, liquidar una transacción con otro agente, aplicar límites de gasto por tarea, o administrar una wallet no custodial. Se complementa bien con los skills cost-aware-llm-pipeline y security-review.

El skill ofrece un árbol de decisión según el caso: si el agente paga una API con cobro 402 en Base (u otra chain soportada), se recomienda usar `agentwallet-sdk` como servidor MCP de pagos con una política de gasto estricta. Si paga en X Layer, se usa el OKX Agent Payments Protocol (del repo `okx/onchainos-skills`), donde el skill antiguo `okx-x402-payment` queda marcado como alias obsoleto. Si en cambio el agente es quien cobra a otros agentes (lado vendedor), hay guías específicas por lenguaje: TypeScript (Express/Hono/Fastify/Next.js), Go (Gin/Echo/net-http), Rust (Axum) y Java (Spring Boot/Java EE/Jakarta); para Python se aclara que puede no existir aún guía oficial y hay que revisar el repo actual de OKX Payments.

Sobre redes soportadas: para `agentwallet-sdk` se recomienda confirmar la cobertura vigente en la documentación del paquete, usando Base Sepolia como entorno de desarrollo seguro y Base mainnet en producción. Para OKX Payments/X Layer, la documentación actual apunta a X Layer (`eip155:196`) con liquidación en USDT0, y se advierte que hay que revisar la documentación del SDK antes de generar código de producción porque cambia con frecuencia.

En cuanto a funcionamiento técnico: el protocolo x402 extiende el código HTTP 402 (Payment Required) en un flujo negociable por máquina — cuando un servidor responde 402, la herramienta de pago del agente negocia el precio, verifica el presupuesto, firma la transacción y reintenta, todo dentro de los límites de política fijados por el orquestador. Toda llamada de pago aplica una "SpendingPolicy" con: presupuesto máximo por tarea, presupuesto acumulado por sesión, lista blanca de destinatarios permitidos, y límites de frecuencia de transacciones por minuto/hora. Las wallets son no custodiales: los agentes tienen sus propias claves mediante smart accounts ERC-4337, y el orquestador define la política antes de delegar, evitando fondos compartidos o riesgo custodial.

La integración MCP expone herramientas estándar invocables por el agente: `get_balance`, `send_payment`, `check_spending` y `list_transactions` (esta última para auditoría). Es clave que la política de gasto se configure con `set_policy` desde la capa de orquestación o un pre-task hook, y NUNCA como herramienta invocable directamente por el propio agente, para evitar que se autoescale su límite de gasto. Se advierte además fijar siempre una versión exacta del paquete (ej. `agentwallet-sdk@6.0.0`) al configurar el servidor MCP, dado que maneja claves privadas y una instalación `npx` sin pin introduce riesgo de cadena de suministro.

Para el flujo del lado comprador con OKX Agent Payments Protocol, se detalla: instalar/referenciar el repo `okx/onchainos-skills`, usar `skills/okx-agent-payments-protocol/SKILL.md` como dispatcher, tratar `okx-x402-payment` como alias deprecado, y exigir confirmación explícita del usuario antes de verificar estado de wallet o ejecutar pagos (no ocultar la ejecución de pagos detrás de una tool call genérica). Para el lado vendedor se listan URLs concretas de guías actualizadas por lenguaje (TypeScript, Go, Rust, Java), recomendando siempre chequear el repo vigente antes de copiar ejemplos de documentación vieja.

El documento incluye un ejemplo extenso en TypeScript de un orquestador MCP que: valida que exista la clave privada de la wallet antes de levantar el subproceso, conecta por stdio pasando solo las variables de entorno necesarias (nunca todo `process.env`), define la política de gasto con `set_policy` verificando que no falle silenciosamente, y aplica un hook `preToolCheck` de "fail-closed" antes de cualquier acción paga, cubriendo cinco casos de error: costo inválido (NaN/Infinity), falla de conectividad con el servicio de pagos, error devuelto por la tool, formato de respuesta inesperado, y presupuesto insuficiente. También aclara instalar el paquete con `npm install -g` antes de configurar el MCP, porque `npx` sin `-y` puede colgarse esperando confirmación en entornos no interactivos.

Como buenas prácticas finales el skill recomienda: fijar presupuestos antes de delegar en sub-agentes (nunca gasto ilimitado), pinnear dependencias con versión exacta y verificar integridad del paquete, usar `list_transactions` en post-task hooks para auditoría, fallar cerrado (bloquear la acción paga) si la herramienta de pago no responde en vez de degradar a acceso sin medición, tratar las herramientas de pago con el mismo escrutinio que el acceso a shell (par con security-review), y probar primero en testnets (Base Sepolia) antes de pasar a mainnet. Cierra con referencias de producción: el paquete npm `agentwallet-sdk`, un PR que lo integró al NVIDIA NeMo Agent Toolkit, la especificación del protocolo en x402.org, los SDKs de OKX Payments en GitHub, el skill de OKX Agent Payments Protocol, y la documentación general de OKX Payments.
