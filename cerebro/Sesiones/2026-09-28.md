## 5. 🩹 Corrección Crítica en Pre-armador de Cotizaciones con IA (`gemini-client.js`)
- **Problema Abordado**:
  - Al presionar `⚡ Pre-armar con IA` en el Cotizador, la solicitud fallaba de inmediato con `Error: Key rechazada o inválida (400)`.
- **Causa Raíz**:
  - `parseQuoteRequest(rawText, catalog)` llamaba a `callGemini(prompt, 'gemini-3.1-flash-lite')` pasando un `string` posicional en lugar de un objeto `{ prompt, model }`.
  - La función `callGemini` desestructuraba `{ prompt } = arguments[0]`, haciendo que `prompt` fuera `undefined`.
  - Google Gemini API recibía un arreglo de partes vacío `parts: [{}]` y rechazaba la solicitud con HTTP 400 (`INVALID_ARGUMENT: required oneof field 'data' must have one initialized field`).
  - La captura de errores de `callGemini` catalogaba erróneamente cualquier 400 como error de clave ("Key rechazada o inválida (400)").
- **Solución Implementada**:
  - Se flexibilizó la firma de `callGemini` para soportar tanto `callGemini({ prompt, ... })` como `callGemini(prompt, model)`.
  - Se agregó validación explícita para evitar payloads vacíos a Google.
  - Se probó y priorizó el modelo `gemini-3.6-flash` (activo y respondiendo en ~1.7s con HTTP 200 en las llaves del pool), con fallback a `gemini-3.1-flash-lite`. Se retiraron modelos dados de baja por Google (`1.5-flash`, `2.5-flash-lite`).
  - Se refinó el reintento ante timeouts o red (`continue` en lugar de romper prematuramente el bucle de modelos).
  - Se refinó la detección de errores para distinguir errores de payload (`400 BAD_REQUEST`) de errores reales de autenticación (`403` o mensaje explícito de clave `api_key`).
  - Actualizado cache-busting a `?v=20260928_v2_ok` en `admin/cotizador.html` y `vendedor/cotizador.html`.
  - Pushed a `origin/main` para desplegar de inmediato en Cloudflare Pages (commit `d1e26e5`).

## 10. ⚙️ PROTOCOLO CRÍTICO: Ejecución Desacoplada de `wa-server` en Windows (Independiente de Antigravity)
- **El Problema**:
  - Si un agente o desarrollador inicia el servidor ejecutando `node src/index.js` directamente en la terminal de Antigravity, el proceso Node se crea como un proceso hijo (*child process*) del shell de Antigravity.
  - Al cerrar Antigravity o finalizar la sesión, Windows mata automáticamente todo el árbol de procesos, apagando el WhatsApp, el despachador de campañas y el conector de correos de la empresa.
- **La Solución Obligatoria (Proceso Desasociado del Sistema Operativo)**:
  - `wa-server` ya cuenta con `start-hidden.vbs` y `run-service.bat`.
  - Para arrancar el servidor desde comandos sin atarlo a Antigravity, se DEBE ejecutar a través de `wscript.exe` como proceso desacoplado del sistema:
    ```powershell
    Start-Process wscript.exe -ArgumentList "start-hidden.vbs" -WorkingDirectory "C:\Users\PC\Desktop\JJ PAPER\wa-server"
    ```
  - Alternativa CMD:
    ```cmd
    cd /d "C:\Users\PC\Desktop\JJ PAPER\wa-server" && start "" wscript.exe start-hidden.vbs
    ```
  - **Comportamiento Garantizado**:
    - `wscript.exe` se inicia bajo el subsistema Windows Explorer / Session Manager.
    - Ejecuta `run-service.bat` en segundo plano sin ventana negra de consola.
    - `run-service.bat` supervisa `node src/index.js`, redirige toda la salida a `logs\wa-server.log` y auto-relanza el proceso ante caídas o reinicios.
    - **Si Antigravity se cierra, la PC se bloquea o el usuario sale del terminal, `wa-server` sigue corriendo indefinidamente en la máquina.**
