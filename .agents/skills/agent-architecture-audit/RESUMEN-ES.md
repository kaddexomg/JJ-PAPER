# agent-architecture-audit

Este skill es un diagnóstico integral para aplicaciones de agentes y LLMs. Su objetivo es auditar el "stack" completo de 12 capas de un sistema de agentes para detectar fallas que suelen quedar ocultas detrás de wrappers, memoria contaminada, fallos en la disciplina de uso de herramientas, bucles de reparación silenciosos o corrupción en el renderizado de las respuestas. El resultado es un informe de hallazgos ordenados por severidad junto con un plan de arreglos que prioriza el código por sobre el prompt.

Se activa de forma obligatoria antes de llevar a producción cualquier aplicación con LLM, al agregar herramientas, memoria o flujos multi-paso, cuando el comportamiento del agente empeora tras sumar capas wrapper, cuando el usuario reporta que "el agente empeoró" o que las herramientas fallan de forma intermitente, cuando el mismo modelo funciona bien en el playground pero falla dentro del wrapper propio, o cuando se lleva más de 15 minutos debuggeando sin encontrar la causa raíz. También es especialmente relevante si distintos agentes del sistema se comportan de forma inconsistente entre sí o si se sospecha de bucles ocultos de retry/reparación que mutan las respuestas. No debe usarse para debugging general de código (usar agent-introspection-debugging), revisión de código, escaneo de seguridad (security-review) ni benchmarking de rendimiento de agentes (agent-eval).

El concepto central son las 12 capas del stack de un agente, cualquiera de las cuales puede corromper la respuesta final: (1) system prompt, (2) historial de sesión, (3) memoria de largo plazo, (4) destilación/compresión de contexto, (5) recall activo, (6) selección de herramientas, (7) ejecución de herramientas, (8) interpretación de resultados de herramientas, (9) formateo de la respuesta, (10) renderizado/transporte en la plataforma, (11) bucles ocultos de reparación/retry, y (12) persistencia de estado o caché.

Describe cinco patrones de falla comunes con sus síntomas típicos: regresión por wrapper (el modelo base responde bien pero el wrapper lo empeora), contaminación de memoria (temas viejos se filtran en conversaciones nuevas, correcciones del usuario no persisten), fallas de disciplina de herramientas (el modelo ignora o simula ejecutar herramientas requeridas solo por texto de prompt, sin enforcement en código), corrupción de renderizado/transporte (la respuesta interna es correcta pero la capa de plataforma la altera al entregarla), y capas ocultas de agentes (procesos silenciosos de retry, resumen o "auto-fix" que corren una segunda pasada de LLM sin que el usuario lo sepa).

El workflow de auditoría tiene cuatro fases: 1) Alcance, donde se define el sistema objetivo, puntos de entrada, stack de modelos, síntomas reportados, ventana temporal y qué capas auditar; 2) Recolección de evidencia, revisando código fuente (loop del agente, router de herramientas, admisión de memoria, ensamblado de prompts), logs, configuración y archivos de memoria, apoyándose en comandos `rg` (ripgrep) de ejemplo para detectar antipatrones como requisitos de herramientas solo en texto de prompt, llamadas LLM ocultas fuera del loop principal, admisión de memoria sin prioridad de corrección del usuario, bucles de fallback/retry, o mutación silenciosa de outputs; 3) Mapeo de fallas, documentando para cada hallazgo el síntoma, mecanismo, capa de origen, causa raíz, evidencia (referencia file:line o log:row) y nivel de confianza (0.0 a 1.0); 4) Estrategia de arreglo, con un orden de prioridad code-first: primero forzar en código los requisitos de herramientas, luego eliminar o acotar agentes de reparación ocultos haciendo explícitos los fallbacks, reducir duplicación de contexto, endurecer la admisión de memoria (priorizando correcciones del usuario sobre afirmaciones del agente), ajustar los disparadores de destilación, reducir la mutación en el renderizado, y convertir el flujo interno a envoltorios JSON tipados en vez de prosa libre.

Define un modelo de severidad de cuatro niveles: critical (el agente puede producir con confianza un comportamiento operativo incorrecto, arreglar antes del próximo release), high (degrada frecuentemente la correctitud o estabilidad, arreglar en el sprint actual), medium (la correctitud suele sobrevivir pero el output es frágil o desperdicia recursos, planificar para el próximo ciclo) y low (cosmético o de mantenibilidad, backlog).

El formato de salida esperado presenta primero los hallazgos ordenados por severidad (más crítico primero), luego el diagnóstico de arquitectura (qué capa corrompió qué y por qué) y finalmente el plan de arreglos ordenado (code-first). Explícitamente indica no empezar con elogios ni resúmenes: si el sistema está roto, decirlo directamente.

Incluye también siete preguntas de diagnóstico rápido (por ejemplo: ¿puede el modelo saltarse una herramienta requerida y aun así responder?, ¿aparece contenido de conversaciones viejas en turnos nuevos?, ¿corre la plataforma una segunda pasada de LLM antes de entregar la respuesta?) que apuntan directamente a un tipo de falla si la respuesta es sí. Y una lista de antipatrones a evitar: culpar al modelo sin antes descartar regresiones de capas wrapper, culpar a la memoria sin mostrar la ruta de contaminación, dejar que un estado actual limpio borre un incidente histórico sucio, tratar prosa en markdown como protocolo interno confiable, o aceptar reglas de "debe usar la herramienta" en texto de prompt cuando el código nunca las hace cumplir.

El skill define un esquema de reporte estructurado en JSON (schema_version "ecc.agent-architecture-audit.report.v1") con secciones para veredicto ejecutivo (salud general, modo de falla principal, arreglo más urgente), alcance (nombre del target, stack de modelos, capas auditadas), findings (severidad, título, mecanismo, capa de origen, causa raíz, referencias de evidencia, confianza, arreglo recomendado) y plan de arreglos ordenado.

Técnicamente, el skill usa las herramientas Read, Write, Edit, Bash, Grep y Glob, y proviene del origen "oh-my-agent-check". Se relaciona con otros skills: agent-introspection-debugging (debug de fallas en runtime como loops, timeouts o errores de estado), agent-eval (benchmarking comparativo de agentes), security-review (auditoría de seguridad de código y configuración), autonomous-agent-harness (configuración de operación autónoma de agentes) y agent-harness-construction (construcción de harnesses de agentes desde cero).
